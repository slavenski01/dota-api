# Хранение и фоновые задания — E02

## Схема данных (E02-T01)

`packages/persistence` использует PostgreSQL и `pg` 8.23.1. Минимальная целевая версия сервера — PostgreSQL 18; интеграционные проверки выполняются на настоящем PostgreSQL 18.4 из `embedded-postgres` 18.4.0-beta.17 (только dev-зависимость). Docker и системная служба для тестов не нужны. В Linux запускать тесты от обычного пользователя, не root.

```sh
npm ci
npm run build:packages
npm run test:persistence
# Для своей уже запущенной PostgreSQL:
# задайте DATABASE_URL в локальном .env, затем
npm run db:migrate
```

`db:migrate` загружает `.env`; остальные секреты в вывод не попадают. Миграции выполняются одной транзакцией под advisory lock. Имена и SHA-256 применённых файлов записываются в `public.dota_migrations`; изменение уже применённого SQL отклоняется. Следующее изменение схемы оформляется новым файлом. Автоматического отката с удалением данных нет.

Модели:

- `profiles`, `matches`, `participants`: идентичность, nullable account ID, индексы по игроку и времени матча. Участник — `(match_id, player_slot)`, неизвестный аккаунт позднее можно уточнить; конфликт известных аккаунтов отклоняется.
- `artifacts`, `parser_runs`, `datasets`: метаданные, SHA-256, происхождение, параметры, исход разборов, версии нормализации и входов. Составные внешние ключи не допускают связь с артефактом/запуском другого матча.
- `records`: неизменяемые снимки проверенных контрактов. Генерируемые колонки совпадают с JSON, индексы событий и состояний сохраняют отрицательные игровые секунды. Представления `match_snapshots`, `participant_snapshots`, `events`, `coverage`, `episodes`, `reports` дают доступ к моделям без копий JSON.
- `record_participants`: связи событий/покрытия с участниками того же матча.
- `episode_reviews`, `report_episodes`, `report_reviews`: история проверок и точные ссылки отчёта на эпизод и версию проверки в том же наборе.

Числовые ID провайдеров хранятся как десятичный текст до 20 цифр; преобразования в JavaScript Number нет. `null`, ноль и пустота сохраняются различными значениями. Неизменяемые таблицы защищены от UPDATE/DELETE триггером. Новое основание анализа — новый набор; пересчитанные эпизоды и отчёты получают новые ID. Позднейшая проверка не меняет ссылку в старом отчёте.

`saveDataset` валидирует контракты и записывает набор транзакционно; при невалидной связи или дубле откатывается весь набор. `insertRecords` и `insertReview` используются внутри `transaction`. Полная проверка evidence, игрового смысла и покрытия остаётся в E05; хранение JSON не доказывает полноту данных.

Интеграционные тесты создают отдельный кластер с временным паролем на loopback и удаляют только свой временный каталог после остановки. Проверяются миграции пустой базы, конкурентный запуск миграций, контрольные суммы, откат DDL/набора, дубли, неверные связи, точность ID, неизвестные значения, история и необходимые индексы. Пользовательская DATABASE_URL не используется тестами.

Источники: [транзакции node-postgres](https://node-postgres.com/features/transactions), [PostgreSQL — ограничения](https://www.postgresql.org/docs/18/ddl-constraints.html), [embedded-postgres](https://github.com/leinelissen/embedded-postgres).

## Файлы и временные отрезки (E02-T02)

`Storage` отделяет файловые операции от PostgreSQL. Локальная реализация принимает поток, пишет в `.tmp/<uuid>.part`, ограничивает размер и длительность, вычисляет SHA-256, выполняет fsync файла и публикует его атомарным hard link без перезаписи. Ключ — `<первые 2 символа SHA-256>/<SHA-256>`. Конкурентная запись одинакового содержимого проверяет уже существующий файл. Только после публикации регистрируются метаданные; транзакция базы никогда не ссылается на частичный файл. Сбой между публикацией файла и COMMIT может оставить полный непривязанный файл: он сохраняется для последующей явной сверки, а не удаляется автоматически.

Сервер разрешает ID через `artifactById`; произвольный путь не является API. `LocalStorage` отклоняет обход каталогов и симлинки; корень принадлежит локальному пользователю сервиса и не должен быть доступен на запись посторонним процессам. Хеш/размер проверяются при повторной публикации и чтении отрезков; `verify` служит проверкой целостности исходников и резервных копий.

Состояния проверяются контрактом и группируются по перспективе и 30 игровым секундам, включая отрицательное время. Сжатый gzip JSON сохраняется отдельным артефактом; `state_segments` индексирует набор, перспективу и окно. Запрос читает пересекающиеся отрезки и возвращает только записи в запрошенных границах, сохраняя маскирование исходной перспективы. Интерполяции, подтверждения координат/видимости и доказательства покрытия здесь нет — это E05/E07.

Начальные предохранители: файл до 1 GiB, запись до 10 минут, отрезок до 4 MiB gzip / 16 MiB после распаковки, запрос до 120 игровых секунд / 64 MiB декодированных данных. Предел исходного файла имеет запас относительно максимума E01 (105.42 MiB); остальные пределы — консервативные ограничения первой реализации, не результаты нагрузочного теста. Автоматического удаления исходников по квоте нет: при нехватке диска запись завершается ошибкой. Интервалы и память уточняются на полном наборе состояний в E05.

`cleanupTemporary` удаляет только файлы `.part` с UUID старше 24 часов и не затрагивает активные записи текущего процесса. Публикуемые исходники, отрезки и непривязанные полные файлы остаются до явного решения владельца. Worker будет запускать эту очистку при старте; общий срок операции ограничен 10 минутами, поэтому 24 часа отделяют брошенные записи от штатной работы.

Резервная копия: сначала завершить `pg_dump` согласованного снимка базы, затем скопировать весь корень Storage без `.tmp` на другой диск, сохраняя структуру ключей. Неизменяемость опубликованных файлов позволяет копировать их после снимка базы; лишние более новые файлы допустимы. Хранить минимум две последние проверенные копии; автоматическое удаление не включено. Для восстановления остановить worker, восстановить базу в отдельную PostgreSQL 18 и файлы в отдельный корень, сверить SHA-256 и размеры всех `artifacts`, затем переключить DATABASE_URL/STORAGE_ROOT и запустить миграции. Отсутствующий или повреждённый файл считается ошибкой восстановления. Автоматизация backup/restore и общие эксплуатационные проверки относятся к E10.

Проверка: `npm run build:packages && npm run test:storage`. Пять интеграционных сценариев охватывают конкурентную запись, обрыв/лимит/отмену, обход путей/симлинки/повреждение, очистку и чтение окна с разделением перспектив. Набор `test:persistence` также прогоняется после новой миграции.

## Очередь и ресурсы (E02-T03)

`packages/jobs` использует pg-boss 12.37.1, собственную схему `pgboss` и очередь `match-processing` с политикой singleton без разных singletonKey. Одна тяжёлая задача активна во всей очереди; дополнительный advisory lock охраняет обработчик. API и worker используют отдельные пулы. Временные ошибки получают максимум два повтора с задержкой от 5 секунд, экспоненциальным увеличением и верхней границей 60 секунд. `JobError(code, false)` завершает задачу без повтора; в очередь/логи записывается код, без текста исключения или секретов.

Время задания — максимум 600 секунд, heartbeat — 10 секунд, проверка отмены/владения попыткой — каждые 500 мс. После аварийного выхода просроченная попытка возвращается очередью в выполнение; обработчики обязаны быть идемпотентными. Результаты/переходы приложения и согласование с очередью подключаются в E02-T04. При плановом завершении worker прекращает приём, отменяет активные обработчики и ждёт остановки процессов.

`runBoundedProcess` запускает команду без shell, через отдельный процесс надзора. Надзор проверяет родителя, время и суммарный RSS группы дочернего процесса каждые 250 мс; при нарушении посылает SIGTERM, через 500 мс — SIGKILL. Потомки останавливаются также после обычного выхода команды. Переменные DATABASE_URL и ключи провайдеров дочерней команде не передаются; stderr не попадает в журналы. Реализация предназначена для macOS/Linux с `/bin/ps`.

Начальные пределы основаны на E01-T03: JVM heap 1 GiB, RSS группы 1.5 GiB (наблюдаемый максимум 735.6 MiB), процесс 120 секунд (наблюдаемые 1.1–2.3 секунды для базового разбора), входной файл до 1 GiB (наблюдаемый максимум 105.42 MiB). Управляющий stdin до 1 MiB, stdout до 64 MiB, stderr до 64 KiB. У Node worker heap до 256 MiB. Контроль RSS периодический, не жёсткий лимит ОС: между измерениями возможен краткий выход за предел. Это ограничения первой версии; полные состояния потребуют повторных замеров в E05. Для файлового входа вызывающая интеграция указывает `inputFile`, а не только путь в аргументах команды.

Worker загружает `.env` корня через `npm run start:worker`, применяет миграции, чистит старые `.part` и подключается к очереди. `--check` проверяет конфигурацию без соединения с базой; без DATABASE_URL обычный запуск выдаёт понятную ошибку. В E02-T03 подключён служебный обработчик `verify_artifact`; обработка матча появляется с машиной состояний E02-T04 и адаптерами E03–E08.

Проверки: `npm run test:jobs` — семь сценариев с настоящей PostgreSQL: два worker, временная/постоянная ошибка и идемпотентный эффект, SIGKILL и восстановление, отмена дочерней команды, ограничения процесса, уборка осиротевшего процесса и запуск/остановка приложения. `npm run smoke` проверяет совместимость CLI/web без базы.

Источники: [pg-boss — worker и отмена попытки](https://github.com/timgit/pg-boss/blob/master/docs/api/workers.md), [политики и параметры очередей](https://github.com/timgit/pg-boss/blob/master/docs/api/queues.md).
