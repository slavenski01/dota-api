# Таймлайн и воспроизведение (E14)

## Воспроизведение и проверка браузера

Оба просмотрщика используют общие часы requestAnimationFrame с монотонным
временем: 0,5× / 1× / 2× / 4×, пауза, шаги и переходы к событиям. На конце
записи воспроизведение останавливается и сохраняет URL. Во время ожидания
интервала часы заморожены, предыдущий кадр явно подписан. После паузы или
буферизации время отсчитывается от нового начала, без накопления пропущенного
настенного времени. Скрытие вкладки ставит просмотр на паузу; возврат сам
не запускает его. Перемотка и смена перспективы также останавливают часы.

Замеры 18 октября 2026 на этой машине, Codex IAB, viewport 626×725:

- Реальный R3, 1×, около 59 с: 116,8 rAF/с, максимальный промежуток 66,8 мс,
  начальная буферизация 17 мс, четыре запроса интервалов, 1781436 байт в кэше,
  HTTP p95 55,5 мс. На 2×: 119,3 rAF/с, максимум 58,2 мс, кэш до 1838733 байт.
- Тестовый матч: около 119,7 rAF/с на 1×; 4× и 0,5× также проверены. Это
  частота вызовов rAF, а не гарантия показанных кадров на любом устройстве.
- Искусственная задержка интервала 5 с дала около 5 с буферизации без скачка
  игрового времени. Отдельный HTTP 503 исправлялся кнопкой повтора. Быстрые
  переходы, границы окон, старый набор и смена перспективы проверены.
- Эпизод из 629,8 с остановился на 630 с: кнопка воспроизведения отключилась,
  URL сохранил время и героя. Пауза в середине игры также сохраняет момент.
- IAB не сообщает `document.hidden` при скрытии своих панелей. Поэтому
  настоящий обработчик visibilitychange проверен через тестовый iframe
  `/__playback_lifecycle`: после скрытия и возврата время осталось
  `600.716834`, просмотр на паузе. Этот стенд доступен только в preview-тесте.

Повторный серверный замер R3 с полным индексом событий и состояний: p50/p95
14,45/17,75 мс, удерживаемый прирост Node heap после GC до 2852992 байт.
Браузерный heap напрямую не измерялся: приведён ограниченный размер кэша,
а не оценка памяти всей вкладки. Вывод метрик включается параметром
`diagnostics=1` только для проверки; без него технических показателей в UI нет.

Проверки: `npm run test:playback`, `npm run test:playback-visual`,
`npm run test:explorer-web`, `npm run typecheck`, production build.
Контракты, Kotlin, persistence и реальная нормализация также проверены.

## Локальное время и сглаживание

Оба ползунка обновляют локальное время через requestAnimationFrame. Ссылка
сохраняется после отпускания, ухода фокуса или шага клавиатуры. История
восстанавливает время, героя и перспективу, включая дробные секунды.

Сглаживаются только координаты полного обзора: два известных наблюдения
живого героя, dt ≤ 0,3 с, отсутствие breakBefore у правой точки, расстояние
≤ min(180, 750 × dt). Экстраполяции нет; позиция старше 0,3 с скрывается.
Смерть, возрождение, скачки, пропуски и unknown не сглаживаются. Старые
наборы используют исходные редкие состояния без интерполяции.

Маркеры показывают время опорного наблюдения и пометку сглаживания. Панель
HP/маны/инвентаря сохраняет реальные состояния и их возраст. Визуальные
точки не меняют evidence, правила анализа или контекст решения.
Браузерная проверка подтвердила возврат 601,125 → 600,125 с, героя из прямой
ссылки и очистку при смене перспективы в обоих просмотрщиках.

## Наблюдения движения

`motion-v1` — отдельные `hero_motion` записи: участник, происхождение,
номинальный шаг, массив реальных игровых времён, тиков, X/Y, состояния жизни
и причин разрыва. Координаты используют проверенный world origin E07.
Обзор команды не подтверждён. Эти записи не являются состояниями HP/маны,
не поступают в правила анализа и не заменяют evidence.

Парсер проверяет позиции на каждом доступном тике, сохраняет их раз в 250 мс
игрового времени. Паузы не создают повторных времён. Между сохранёнными
наблюдениями накапливаются признаки пропуска, смены сущности/жизни,
неизвестных координат и скачка. Скачок: перемещение за тик превышает
`max(48, 900 × dt)` игровых единиц. Это консервативная граница для отрисовки,
а не доказательство телепорта. Очень короткие изменения между тиками
не восстанавливаются. Отсутствующее положение остаётся null.

Контракт проверяется в Kotlin и TypeScript: порядок времён и тиков,
совместная известность X/Y, причина неизвестного положения, длина окна.
Записи упаковываются в 30-секундные gzip-сегменты, отдельно от тяжёлых
состояний, с SHA-256 и неизменяемыми ссылками в `dota.motion_segments`.
Лимиты чтения не выше `readStateWindow`: длина окна, число сегментов,
сжатые и распакованные байты ограничены, каждый файл проверяется по хешу.

Версия нормализации `e14-motion-v1-250ms` создаёт новый datasetId через
«Повторить обработку» на странице матча. Старые наборы доступны с прежним
шагом 5 с / 1 с возле смертей. Заметки, проверки и отчёты остаются привязаны
к исходным наборам. Перенос или перезапись старых данных не выполняются.

## Загрузка интервалами

API `explore?resource=playback&version=playback-v1&bucket=N` выдаёт 30 секунд
с наблюдениями до начала окна (5 с для состояний, 1 с для движения) и
до 0,3 с после конца для соседней позиции. Отображаемое время ограничено
основным окном. На границах исходные наблюдения имеют те же ID и времена.
Для эпизода передаётся episodeId, доступ и окно проверяются сервером.
Командная перспектива возвращает пустые ряды без чтения полного обзора.

Кэш включает версию, набор, аккаунт, перспективу, эпизод и матч. До четырёх
окон и 8 MiB сериализованных данных; текущий интервал закреплён, соседние
предзагружаются. Ответ ограничен 4 MiB. Отменённый запрос не записывает
данные после смены контекста; неудачная предзагрузка не блокирует текущий
кадр. Переход внутри окна не отправляет запросы за отдельными кадрами.

Замер `scripts/validate-playback.mjs` на R3 (3065,8 с, 103 интервала):
серверное чтение p50 8,70 / p95 13,96 мс, ответ p50 329091 / max 753984
байт. Кэш: максимум 2388571 сериализованных байт, четыре окна; прирост
Node heap после GC до 2872264 байт. Это чтение из локального Storage и БД,
без HTTP, браузера и React; их время проверяется отдельно. Исходные данные
и полный протокол — в data/e14-validation/playback-summary.json.
