# Контракты данных и протокол парсера

E14 добавляет транспортный вид `hero_motion` (`motion-v1`) с компактными реальными наблюдениями. Он хранится в отдельных сегментах, не в таблице аналитических записей. Старые сообщения 0.1.0 сохраняют прежний смысл. Новый pipeline `e14-motion-v1-250ms` использует расширенный контракт; подробности и измерения — в [playback.md](playback.md).

Дата: 12 октября 2026 года. Задача: E00-T03. Версия данных: `0.1.0` (черновая); версия транспорта: `1.0.0`.

Канонический источник — [contracts.schema.json](../packages/contracts/schema/contracts.schema.json), JSON Schema Draft 7. TypeScript использует Ajv, Kotlin — Networknt; оба проверяют один файл схемы и дополнительные связи между полями. Схемы описывают восемь видов записей и NDJSON. Они не подтверждают возможность извлечь эти данные из реального реплея: это проверяется в E01.

## Реализация и воспроизводимость

- `@dota/contracts` экспортирует типы, `validateRecord`, `validateMessage`, `validateRequest`, `readMessages`, `readRequest`, `encodeMessage`, `encodeRequest`, `ContractError` и константы версий/размера строки.
- `npm run generate --workspace=@dota/contracts` создаёт TypeScript-типы и модуль схемы из JSON. Генерация также входит в `build` и `typecheck`; каталог `src/generated` исключён из Git и не редактируется вручную.
- Gradle включает тот же JSON как ресурс в дистрибутив Kotlin CLI. Запуск из другой рабочей папки поддержан. `$id` схемы — идентификатор, а не адрес для скачивания: проверке не нужен сетевой запрос.
- Дополнительные проверки в [validation.ts](../packages/contracts/src/validation.ts) и [ContractValidator.kt](../services/replay-parser/src/main/kotlin/local/dota/parser/ContractValidator.kt) согласуются общими примерами. Использование только JSON Schema без этих проверок не равно полной проверке контракта.

Зафиксированы Ajv `8.20.0`, ajv-formats `3.0.1`, json-schema-to-typescript `16.0.0`, Networknt json-schema-validator `2.0.4`, Jackson databind `2.18.4`. Транзитивные версии находятся в npm/Gradle lockfiles. Основания выбора: [Draft 7](https://json-schema.org/draft-07), [валидация Ajv](https://ajv.js.org/guide/getting-started.html), [Networknt 2.0.4](https://github.com/networknt/json-schema-validator/tree/2.0.4), [генератор типов](https://github.com/bcherny/json-schema-to-typescript).

## Общие соглашения

Все объекты закрыты: неизвестные поля отклоняются. Обязательность поля не отменяется его nullable-типом: неизвестный `accountId` передаётся как `null`, а не пропускается. Валидатор не подставляет значения по умолчанию, не удаляет поля и не преобразует строки в числа.

| Значение | Представление и смысл |
| --- | --- |
| `matchId`, `accountId`, `steamId64`, `heroId`, `aspectId`, `itemId`, `resourceId` | Десятичная строка из 1–20 цифр без знака и ведущих нулей, кроме самой строки `"0"`. Не преобразовывать в JavaScript `Number`. Формат не подтверждает существование ID и не проверяет диапазон конкретного провайдера. |
| `id`, ссылки на записи, артефакт, набор, запрос | Непустой непрозрачный ID до 128 ASCII-символов: буквы, цифры, `.`, `_`, `:`, `-`; первый символ — буква или цифра. В пределах потока ID записей уникальны. |
| `playerSlot` | Число: 0–4 для Radiant, 128–132 для Dire. Контракт MVP рассчитан на обычный матч 5×5. Участник определяется парой `matchId + playerSlot`; закрытый аккаунт этому не мешает. |
| Игровое время | Число секунд, дробная часть разрешена; отрицательные значения до начала матча сохраняются. Суффикс `Seconds` обязателен в соответствующих полях. Окно включает обе границы, начало не позже конца. |
| `tick` | Неотрицательное безопасное целое либо `null`. Это исходный тик реплея; постоянная формула перевода в секунды не предполагается, паузы требуют отдельной нормализации. |
| Календарное время | Валидная строка UTC вида `2026-10-12T00:00:00Z` или с 1–3 знаками миллисекунд перед `Z`. Локальные смещения не принимаются; UI преобразует время отдельно. |
| Метрики и координаты | JSON-числа в пределах ±`9007199254740991`; статистические счётчики — неотрицательные целые, HP/мана/длительности — неотрицательные числа. Дробные числа используют обычную точность JavaScript; точность произвольных десятичных дробей не обещается. |
| `null`, `0`, `[]` | Разные значения. `null` — значение неизвестно/не получено; `0` — измеренный ноль. Известный пустой инвентарь допустим только как наблюдение `known`, отсутствие событий подтверждается записью покрытия. |
| `Sha256` | Ровно 64 строчных шестнадцатеричных символа. Формат хеша проверяется, соответствие реальному содержимому — задача хранения/аналитики. |

Каждая запись содержит `schemaVersion`, `kind`, `id`, `matchId`, `provenance`. Происхождение включает `source` (`replay`, `opendota`, `steam`, `manual`, `derived`, `fixture`), календарное время получения `acquiredAt`, nullable `artifactId`/`sourceVersion` и `inputIds`. Для производного факта основания перечисляются в `inputIds` и evidence-ссылках. Хеши/размеры артефактов и история наборов реализованы в E02; полная проверка evidence относится к E05.

## Восемь видов записей

| `kind` | Содержание |
| --- | --- |
| `match` | Время начала, длительность, режим, патч, победа Radiant; неизвестные сведения допускают `null`. |
| `participant` | Slot и команда, nullable ID аккаунта/героя/аспекта, роль с источником и ссылка на её основание, итоговая статистика. Неизвестная роль не блокирует статистику. Команда обязана соответствовать slot. |
| `event` | Игровое время, nullable tick, ссылки на покрытие; `data.type` выбирает смерть, предмет, объект или драку. Смерть содержит жертву, nullable убийцу и признак после выкупа; предмет — участника, ID и действие; объект — ID/тип/команды; драка — окно, участников и определение группировки. |
| `hero_state` | Slot, время, перспектива, видимость, позиция, HP, мана, жив/мёртв, инвентарь, ресурсы способностей/предметов, последняя известная позиция, ссылки на покрытие. Значения оформлены как наблюдения. |
| `coverage` | Набор, вид данных, участники, временное окно, статус, nullable разрешение по времени/причина, evidence-ссылки. |
| `job` | Стадия исполнения, уровень данных, готовность отчёта, ограничения, nullable ошибка с кодом/текстом/признаком допустимости повтора. |
| `episode` | Набор, участник, окно, момент решения, сигналы правил с версиями и хешами конфигурации, evidence-ссылки, nullable ручная проверка. |
| `report` | Набор, участник, время создания, факты/гипотезы с evidence, эпизоды и версии ручных проверок, причины пропуска правил, nullable следующее действие, версии входов аналитики. |

Типы событий не являются реализацией алгоритмов их извлечения. Например, запись `fight` хранит явно заданное определение группировки, но не доказывает корректное выделение драки. Правила `D01`, `D02`, `L01`, `I01`, `F01` пока имеют только идентификаторы контракта; реализация относится к E06.

## Наблюдения, перспективы и покрытие

Известное наблюдение: `{"status":"known","value":0,"observedAtSeconds":600.25}`. Неизвестное: `{"status":"unknown","value":null,"reason":"Данные не извлечены"}`. Вместо `unknown` допустимы `unavailable` (подтверждённая недоступность) и `error` (ошибка получения). Причина обязательна; отсутствие никогда не преобразуется в ноль. Времена всех вложенных наблюдений и последней известной позиции не могут быть позже `hero_state.gameTimeSeconds`.

Позиция задаётся в мировых координатах `{x, y, z, coordinateSystem: "world", mapVersion}`; `z` и `mapVersion` допускают `null`. Это не пиксели и не обещание готового преобразования на подложку. E07 использует отдельную приблизительную подложку 7.40 и версионированную проекцию; патч реплея из неё не выводится.

`perspective` — либо `{mode: "omniscient"}`, либо `{mode: "team", team: "radiant" | "dire"}`. В командной перспективе текущие позиция, HP, мана, состояние жизни, инвентарь и ресурсы допустимы как `known` только при подтверждённой видимости `visible`. При `hidden` или неизвестной видимости они должны быть неизвестными/недоступными/ошибочными. Последняя известная позиция хранится отдельно со своим временем. Полный обзор допускает фактические состояния, но не должен подаваться в контекст оценки решений команды. Камера в этот черновой формат не включена; её отсутствие не означает отсутствие видимости и не блокирует MVP.

Каждый ресурс отдельно хранит `cooldownRemainingSeconds` и `canUse` как наблюдения. Нулевой cooldown не позволяет автоматически заполнить `canUse: true`: ограничения маны, контроля, цели и прочие условия проверяются при извлечении/нормализации.

`coverage.field`: `deaths`, `items`, `objectives`, `fights`, `positions`, `visibility`, `resources`, `statistics`, `time`. Одна запись относится к конкретным `datasetId`, `participantSlots` и `window`:

| Статус | Значение |
| --- | --- |
| `present` | Данные в заявленном диапазоне получены; нужны непустые `evidenceIds`. Пригодность для правила проверяется отдельно. |
| `empty` | Подтверждено отсутствие событий/значений в данном диапазоне; нужны непустые `evidenceIds`. |
| `missing` | Данные не извлечены/не поступили; обязательна причина. |
| `error` | Получение или проверка завершились ошибкой; обязательна причина. |
| `unknown` | Семантика/полнота пока не установлена; обязательна причина. |

`resolutionSeconds` описывает период снимков, если известен; `null` его не выдумывает. Валидатор проверяет форму покрытия и наличие ссылок, но ещё не разрешает ссылки и не сверяет заявление с содержимым полного набора. Это E05-T03. Поэтому `complete` транспорта и пустой массив событий сами по себе не означают `coverage: empty`.

## Задание, ручная проверка и отчёт

Стадии задания: `queued`, `resolving`, `downloading`, `parsing`, `validating`, `analysing`, `ready`, `unavailable`, `failed`, `cancelled`. `dataLevel` отдельно принимает `none`, `summary`, `events`, `replay_context`; `reportStatus` — `not_requested`, `pending`, `ready`, `failed`. Машина переходов, очередь и история снимков реализованы в E02-T04. При `failed`/`unavailable` объект ошибки обязателен, при остальных статусах он равен `null`; `ready` требует уровень данных выше `none`. Ошибка текстового этапа допускается при готовых данных.

У эпизода `decisionTimeSeconds` входит в его окно. `review: null` означает отсутствие встроенной ручной проверки. Отдельная история оценок в E07 хранит собственную версию, статус `unreviewed`/`confirmed_error`/`justified`/`uncertain`, объяснение, автора, время, материал (`timeline`, `map` или `dota_client`) и перспективу. `unreviewed` позволяет отозвать прежнюю оценку без удаления истории. Подтверждённая ошибка требует непустой альтернативы. `timeline` обозначает просмотр событий/состояний. Новая оценка `map` требует доступных позиций и полного обзора; необязательное обратно совместимое поле `mapContext` сохраняет `backgroundVersion`, `projectionVersion`, `imageSha256`. Сервер заполняет его сам; старые оценки без поля остаются действительными. `dota_client` обозначает добровольный ручной просмотр в клиенте, а не видео в сервисе. ID эпизода обозначает неизменяемую версию эпизода/набора: пересчёт создаёт новый ID, изменение проверки увеличивает её версию. Последняя оценка читается через API reviews, не переписывает автоматический episode snapshot.

Отчёт разделяет `fact` и `hypothesis`, обе категории требуют evidence. Ручной вердикт хранится в эпизоде, а `reviewRefs` отчёта указывают использованную версию; каждый такой эпизод обязан присутствовать в `episodeIds`. Следующее действие различает `confirmed_practice`, `experiment`, `review_episode`. Версии парсера, нормализации, правил, SHA-256 skill и nullable модель/хеш промпта фиксируются в `versions`. Истинность evidence, актуальность ручных проверок и основание для `confirmed_practice` проверяются между записями в E05/E08, а не выводятся из прохождения схемы.

## NDJSON через stdin/stdout

Один запуск `replay-parser --protocol` обрабатывает ровно один запрос. stdin — одна строка UTF-8 JSON с завершающим LF, затем EOF. Пример запроса находится в [request.ndjson](../packages/contracts/fixtures/request.ndjson):

```json
{"protocolVersion":"1.0.0","schemaVersion":"0.1.0","type":"parse","requestId":"request-fixture","replayPath":"/synthetic/not-a-real-replay.dem","expectedMatchId":"9007199254740993"}
```

`replayPath` — локальный путь для доверенного worker, не публичный HTTP-параметр. В E01-T03 подключена Clarity 5.0.1: CLI проверяет локальный файл, внутренний match ID и завершённость разбора; выдаёт матч, десять участников, смерти и записи покрытия. Подробности — в [отчёте парсера](replay-parser-validation.md). CLI извлекает всех участников; потребитель явно выбирает нужного.

stdout содержит только NDJSON-сообщения. Все сообщения включают `protocolVersion`, `schemaVersion`, `requestId`, `sequence`, `type`:

| `type` | Дополнительные поля и условие |
| --- | --- |
| `record` | `record` — одна из восьми записей. Все записи потока относятся к одному `matchId` и имеют уникальные `id`. |
| `complete` | `recordCount` — точное количество предшествующих записей. Терминальное успешное сообщение. Нулевой счётчик допустим, но не подтверждает наличие пригодных данных. |
| `error` | `code`: `not_implemented`, `invalid_replay`, `parse_failed` или `cancelled`; непустой `message`. Терминальный неуспешный исход. |

`sequence` начинается с 0 и увеличивается на каждой записи; терминальное сообщение имеет `sequence`, равный числу записей. `requestId` одинаков во всём потоке. Требуется ровно одно терминальное сообщение, после него — EOF. Смешение версий/матчей/запросов, повторы ID, пропущенный номер, неправильный счётчик, данные после завершения и обрыв потока отклоняются.

Разделитель — LF; CRLF принимается. Каждая строка содержит ровно один JSON-документ, без BOM и некорректного UTF-8; пустые строки запрещены. Максимум — 1 048 576 байт на строку, включая необязательный CR, исключая LF. Завершающий LF обязателен. Производитель выдаёт компактный JSON; экранированный `\n` внутри строки JSON допустим.

Диагностика направляется в stderr и не включается в данные матча. После разбора `parser-checks` содержит агрегированные счётчики проверок без ID, имён и путей. Валидатор выдаёт краткий `contract-error: <code>` без исходного документа и пути. Обычные команды `--help`, `--check`, `--version` имеют прежний диагностический формат и не являются NDJSON-протоколом.

| Команда/исход | Код завершения |
| --- | --- |
| `--validate-ndjson`: корректный поток, включая корректно оформленный терминальный `error` | 0 — успешно проверен формат |
| `--protocol`: завершённый разбор поддержанного реплея | 0 и записи + NDJSON `complete` |
| `--protocol`: отсутствующий/повреждённый/несовместимый файл или другой ID | 3 и NDJSON `error: invalid_replay` либо `parse_failed` |
| Некорректный запрос/поток или неподдержанные аргументы | 2; диагностика в stderr |

`readMessages` и `--validate-ndjson` потоково выдают уже проверенные отдельные записи до проверки оставшегося входа. Потребитель обязан дочитать до EOF, проверить терминальный `complete` и код завершения процесса 0, сопоставить `requestId`/`matchId` с исходным запросом и лишь затем публиковать результат. Ранний выход из async iterator не подтверждает целостность потока. При ошибке уже выданные записи остаются предварительными. Общие ограничения времени/числа записей и отмена процесса относятся к будущему worker в E04.

Из корня проекта после установки зависимостей:

```sh
npm run typecheck

npm run test:contracts
npm run smoke

./services/replay-parser/build/install/replay-parser/bin/replay-parser --protocol \

# Проверить полный ранее сохранённый поток; stdout — нормализованные сообщения
./services/replay-parser/build/install/replay-parser/bin/replay-parser --validate-ndjson \
  < /path/to/messages.ndjson
```

[Контрольные записи](../packages/contracts/fixtures/records.json) и [некорректные варианты](../packages/contracts/fixtures/invalid-cases.json) синтетические: источник `fixture`. Это проверка совместимости языков, а не результаты матчей пользователя. Проверяется круговой обмен TypeScript → Kotlin → TypeScript для всех видов записей, событий и перспектив, сохранение строковых ID больше `2^53`, нулей, null, отрицательного и дробного времени, ошибки формы/связей/потока, CRLF и разбиение UTF-8 на произвольные байты. JVM-процесс запускается вне папки проекта для проверки упаковки схемы.

## Изменение контракта после E01

Версии данных и транспорта независимы; текущие валидаторы принимают только точные значения `0.1.0` и `1.0.0`. Принцип «игнорировать неизвестные поля» не используется. Изменение формы или смысла поля требует новой версии данных; изменение конверта/последовательности — версии транспорта.

Пока версия данных черновая, допустима явная миграция `0.1.0`: записать причину и преобразование в этот документ и журнал плана, обновить схему, примеры, оба семантических валидатора и проверки; указать, какие сохранённые наборы пересоздаются и как меняются их ID/хеши. Молча переинтерпретировать старые данные нельзя. После появления сохранённых данных предпочтительна новая версия с отдельным мигратором и примерами старого/нового формата.

Версии схемы и транспорта в E01-T03 не изменились. `not_implemented` остаётся допустимым кодом контракта, текущий CLI его не выдаёт. ID базового набора включают SHA-256 реплея и `basic-v1`; изменение алгоритма требует новой версии извлечения. `artifactId: replay-sha256-<hash>` обозначает входной файл, но не создаёт запись хранилища. Повторные результаты отличаются только `acquiredAt`.

В E01-T04 добавлен отдельный исследовательский формат `context-research-v1` через `--research-context FROM TO`: запрос на stdin прежний, ответ — один JSON, **вне NDJSON-контракта**. Он не является `hero_state`, не меняет `0.1.0`/`1.0.0` и не поступает в worker. Ошибка аргументов/запроса даёт код 2 и stderr, ошибка реплея или пустое окно — код 3 и JSON `status: error`, успешное исследование — код 0 и `status: research_only`. Выходной JSON не ограничен размером строки NDJSON; число снимков, длина окна и кандидаты ограничены отдельно. Его нельзя подавать в `--validate-ndjson`.

Кандидатные координаты, необработанные таймеры, unit flags и имена/handles ресурсов требуют проверки смысла и нормализации перед общим контрактом. Сетевые handles не подставляются вместо стабильных числовых ID. Смысл признаков видимости пока не подтверждён, поэтому все текущие поля обеих командных проекций неизвестны, `lastKnownPosition: null`, `canUse: unknown`. Полный исследовательский JSON содержит ретроспективные данные и не разрешён как контекст оценки решения. [Матрица возможностей и ограничения](replay-capabilities.md) фиксируют проверки для E05-T02/T04 и E07-T02. Клиент необязателен; поле `clientVerified: false` описывает отсутствие клиентской сверки, а не блокировку готовности исследования.

Дальнейшие границы: E01-T03 подтвердил базовые возможности Clarity, E01-T04 завершена как исследование с ограничениями и без обязательного просмотра в клиенте; E02 добавляет хранение и историю версий; E04 подключает дочерний процесс к worker; E05 проверяет полные наборы и покрытие; E07 строит карту/таймлайн/состояния; E08 проверяет доказательность отчёта. Видео остаётся вне MVP.


## Хранение контрактов в E02

Формат `0.1.0` и NDJSON не менялись. `packages/persistence` сохраняет валидированные записи как неизменяемые snapshots, точные строковые ID и исходные null. Версия набора, эпизода, отчёта и ручной проверки имеет отдельную идентичность; SQL-связи проверяют матч/набор и удерживают использованную отчётом проверку. `job` хранится отдельно как изменяемый снимок с неизменяемой историей и транзакционными контрольными точками. Поле статуса не заменяет уровень данных или готовность текста. Полная проверка evidence/покрытия остаётся в E05/E08. См. [схему, API и интеграционные проверки](persistence.md).

## Дополнение E04

HTTP состояние задания дополнено `artifactId`, `accountId` и `progress`
(phase, bytes, totalBytes или null). Версии базовых NDJSON/record-контрактов
не меняются. В E06 успешный импорт/разбор/отбор завершает задание `ready`;
`analysisId` ссылается на неизменяемый результат, текст ещё не запрошен.
Подробнее: [импорт](replay-import.md).


## Дополнение E06

Базовые записи `episode`/`RuleSignal` и NDJSON 0.1.0 не изменены. Аналитический
HTTP-контракт `e06-v1` описан типами `RuleResult`, `AnalysisRun`, `SelectedEpisode`
в `@dota/analysis`: конфигурация, evidence, три исхода правил и явная полнота.
Полный результат хранится отдельно от сырых записей парсера, сами эпизоды —
в `dota.records`. [API и правила версионирования](analysis.md).

E09: необязательное `HeroState.lane` (`formatVersion: lane-v1`) хранит отдельные NumberObservation для lastHits/experience. Старые записи валидны без поля; отсутствие не означает ноль. Поле доступно только в ретроспективе; маскирование командного контекста его не передаёт.
