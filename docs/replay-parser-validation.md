# Проверка Kotlin/Clarity: E01-T03

Дата: 12 октября 2026 года. Статус: DONE. Область — базовые события и статистика; восстановление обзора и состояний героев относится к E01-T04.

## Результат

Kotlin CLI разбирает пять локальных `.dem` из [E01-T02](replay-download-validation.md) через Clarity и выдаёт проверяемый NDJSON. На каждом файле выполнено два полных последовательных запуска отдельной JVM. Подтверждены внутренний match ID, единственный выбранный участник, команды, слоты и герои всех десяти игроков. Все **450 сравнений** девяти итоговых показателей с сохранёнными ответами OpenDota совпали; число событий смерти совпало с итоговым счётчиком каждого из 50 участников. Пять проверок ошибочного входа завершились терминальным `error`, без записей данных и `complete`.

Публичный отчёт обезличен: R1–R5 — локальные метки. Идентификаторы, ники, конкретные показатели игроков, файлы и хеши находятся только в исключённой из Git папке `data/`. Они не нужны для чтения этого отчёта.

## Версии и реализация

| Компонент | Проверенная версия |
| --- | --- |
| Clarity | 5.0.1 |
| clarity-protobuf | 7.1, строго закреплена вместо плавающего диапазона библиотеки |
| snappy-java / slf4j | 1.1.10.7 / 2.0.17 |
| Kotlin / Gradle / JVM | 2.4.20 / 9.5.1 / JDK 21.0.11 |
| Проверяющий процесс | Node.js 26.3.0, macOS arm64 |

Прямые зависимости и транзитивные версии записаны в Gradle lockfile. Runtime использует `slf4j-nop`: сообщения библиотеки с исходными значениями не попадают в диагностический поток. Наши сообщения ошибок не содержат путей, ID или исходного текста исключений.

[ReplayParser.kt](../services/replay-parser/src/main/kotlin/local/dota/parser/ReplayParser.kt) использует `SimpleRunner` с Kotlin-методами `@OnEntityCreated`, `@OnTickEnd`, `@OnMessage` и `@OnCombatLogEntry`. Их обнаружение подтверждено реальными результатами и обязательными проверками обработанных часов, финального блока и участников. `MappedFileSource` закрывается через `use`.

## Что извлекается

| Данные | Источник и границы |
| --- | --- |
| Матч | `CDemoFileInfo` и `CDOTAGamerulesProxy`: match ID, режим, победитель, дробная игровая длительность. Календарное начало и patch остаются `null` |
| Участники | `CDOTA_PlayerResource`, явные team/teamSlot; SteamID сверяется с эпилогом. Account ID выводится только для стандартного SteamID индивидуального аккаунта. Слоты не выводятся из порядка списка |
| Итоговая статистика | K/D/A, last hits, denies, урон героям и зданиям; GPM/XPM вычисляются как `floor(total * 60 / duration)` из накопленных золота/XP. Снимок берётся в первом тике состояния 6, до последующей анимации |
| Смерти | Combat log: подтверждённый герой, явно исключённые иллюзия и реинкарнация; события после `m_flGameEndTime` исключены. Герой однозначно сопоставлен со слотом через метаданные участников |
| Неизвестные сведения | `role`, `aspectId`, `killerSlot`, `afterBuyback` остаются `null`. Последние два не восстанавливаются догадкой по имени источника урона |
| Происхождение | Версия `basic-v1/clarity-5.0.1/protobuf-7.1`, время извлечения, SHA-256 исходного `.dem` в `artifactId`; ID записей/набора включают SHA-256 и версию извлечения |

Важная найденная особенность: чтение статистики в самом конце файла завышало некоторые показатели относительно OpenDota; после фиксации снимка на окончании матча все 450 сравнений совпали. В одном реплее есть и смерть после окончания матча: её исключение необходимо для совпадения KDA. Это воспроизведённые результаты, а не общее обещание поддержки всех патчей.

## Игровое время и покрытие

Часы вычисляются по `CNETMsg_Tick`, интервалу из `CSVCMsg_ServerInfo` и полям паузы:

```text
absoluteSeconds = ((paused ? pauseStartTick : serverTick) - totalPausedTicks) * tickInterval
matchSeconds = absoluteSeconds - gameStartTime
```

Тики демо и серверные тики имеют разные начала отсчёта; фиксированная частота 30 Гц в коде не используется. Начало и конец матча сверяются независимо между game rules и событиями изменения состояния combat log. На реальных файлах проверено **шесть пауз в трёх реплеях**: часы не растут во время паузы и не идут назад после неё. Отрицательное предматчевое время сохранено. Дополнительно unit-тесты проверяют две последовательные паузы, другую частоту тиков и некорректные счётчики.

`CombatLogEntry.timestamp` уже исключает паузы; для события из него вычитается только время начала. `timestampRaw` не подставляется вместо него. Combat log может поступать пачками: `event.tick = null`, поскольку тик доставки сообщения не доказывает тик самого события. Точное соответствие каждого события тику и ручная сверка таймкодов в клиенте **не подтверждены**.

Покрытие смертей определяется отдельно для каждого слота, от наблюдённого предматчевого времени до окончания. Требуются нулевой исходный счётчик, однозначная семантика записей и совпадение их количества с финальной статистикой. При расхождении статус `unknown`; ноль событий становится `empty` только после этих проверок. Снимок статистики имеет окно из одной точки, отсутствующие поля остаются `null` и дают `unknown`. `time: present` относится к проверке часов в этом окне, а не к экспортированному ряду состояний героев. Межзаписная проверка наборов и пригодность для аналитических правил остаются E05.

Не извлекаемые ряды — предметы, объекты, драки, позиции, обзор и ресурсы — не получают фиктивного покрытия. Отсутствие записи покрытия не означает `empty`.

## Воспроизводимость, время и память

[validate-replays.mjs](../scripts/validate-replays.mjs) читает локальный манифест E01-T02, проверяет SHA-256 входа, валидирует поток TypeScript-кодеком, сверяет данные и повторяет запуск. Сравнение исключает только `provenance.acquiredAt`; весь остальной NDJSON, включая ID, порядок и дробные времена, совпадает. Входные данные не обновлялись сетевым запросом во время сравнения.

Каждый замер включает запуск отдельной JVM, разбор, SHA-256 и выдачу NDJSON. Heap ограничен `-Xmx1g`; peak RSS измерен `/usr/bin/time -l` и включает память вне Java heap. Кэш файлов ОС не очищался: это измерения на данной машине, не нагрузочный тест. Таблица финального прогона приведена ниже.

| Образец | Первый запуск, с | Повтор, с | Максимальный RSS двух запусков, MiB |
| --- | ---: | ---: | ---: |
| R1 | 2.327 | 1.350 | 689.7 |
| R2 | 1.227 | 1.206 | 677.4 |
| R3 | 1.634 | 1.640 | 735.6 |
| R4 | 1.201 | 1.146 | 667.6 |
| R5 | 1.500 | 1.476 | 703.1 |

Полная локальная доказательная база: `data/parser-validation/2026-10-12-e01-t03/run/`. Там находятся оба NDJSON каждого файла, stderr, замеры `time`, 450 сравнений, нормализованные SHA-256, ошибочные файлы и `summary.json`. Исходные ответы/реплеи указаны в манифесте E01-T02. Скрипт допускает пути манифеста и результатов только внутри `data/` и не содержит конкретного аккаунта.

## Ошибки и проверки

| Случай | Результат |
| --- | --- |
| Отсутствующий файл | `invalid_replay`, код 3 |
| Постороннее содержимое вместо `.dem` | `invalid_replay`, код 3 |
| Реальный файл, обрезанный наполовину | `invalid_replay`, код 3 |
| Корректный файл с другим ожидаемым match ID | `invalid_replay`, код 3 |
| Читаемые заголовок и эпилог, но удалённый игровой поток и stop marker | `parse_failed`, код 3 |

Полный разбор требует совпадения ожидаемого ID, Source 2 Dota, `CDemoStop`, идентичного `CDemoFileInfo`, десяти однозначных участников, финального снимка и согласованных часов. EOF сам по себе не означает успех: Clarity может завершить чтение на обрыве. Сначала проверяется весь ограниченный базовый результат, затем выдаются записи и `complete`. Верхний предел накопленных смертей — 100 000; рабочие лимиты файлов, времени и параллелизма проектируются в E04.

Проверки: пять Kotlin unit-тестов; 56 тестов контрактов; пять smoke-тестов; typecheck всех workspaces; production-сборка web/worker и Gradle `build installDist` с lockfile без `--write-locks`; десять полных разборов и пять ошибочных запусков. Команды:

```sh
npm run typecheck
NEXT_TELEMETRY_DISABLED=1 npm run build:ts
npm run build:parser
npm run test:contracts
npm run smoke
node scripts/validate-replays.mjs \
  data/replay-validation/2026-10-12-e01-t02/manifest.json \
  data/parser-validation/2026-10-12-e01-t03/run
```

В sandbox macOS замеру `time -l` может требоваться разрешение на `sysctl`; это ограничение измерителя, а не ошибка реплея. Тесты реальных файлов намеренно не включены в обычный `build`: локальные персональные входы не распространяются с репозиторием.

## Границы результата и источники

Подтверждены только пять завершённых матчей выбранной выборки с десятью участниками. Source 1, боты, нестандартные режимы и старые/будущие патчи не проверены. Иллюзии проверены unit-тестом; реинкарнации, паузы и постматчевое событие — также реальными файлами. Отчёт не подтверждает обзор, позиции, инвентарь, условия использования способностей, убийцу или выкуп. Идентичность героя и счётчики не заменяют проверку контекста решений.

Первичные источники: [релиз Clarity 5.0.1 в Maven Central](https://repo.maven.apache.org/maven2/com/skadistats/clarity/5.0.1/), [protobuf 7.1](https://repo.maven.apache.org/maven2/com/skadistats/clarity-protobuf/7.1/), [Clarity](https://github.com/skadistats/clarity), [пример итоговой таблицы](https://github.com/skadistats/clarity-examples/blob/master/src/main/java/skadistats/clarity/examples/matchend/Main.java), [поля времени и участников в парсере OpenDota](https://github.com/odota/parser/blob/master/src/main/java/opendota/Parse.java). Для API использованы исходники именно выпущенного JAR: пример на GitHub содержит устаревший `getByDtName`, которого в Clarity 5.0.1 уже нет. Подтверждение сравнения с OpenDota опирается на локальные ответы E01-T02, а не на совпадение алгоритма двух парсеров.
